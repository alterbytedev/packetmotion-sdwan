# Device interface, VLAN and advertisement plan

Date: 2026-10-22. Status: approved for sequential implementation. Read-only discovery, candidates, current-IP telemetry and dedicated static LAN/VLAN safe commit are implemented. WAN/DHCP, management-path changes, multi-prefix routing and forwarding remain pending. Physical activation requires the lab gates below. See [current delivery and Hub evidence](../operations/interface-management.md).

## Outcome and current baseline

Make `/dashboard/devices/[id]` support reviewed interface configuration, including IPv4 addressing and routed IEEE 802.1Q VLAN subinterfaces. Advertise explicitly selected LAN subnet prefixes through the existing WireGuard/FRR design. Preserve the existing dashboard, authentication, tabs and shared UI conventions. The requested VeloCloud-like experience is a usability reference, not a promise of feature parity.

Today Underlay renders heartbeat interface name, enabled state and MTU, including loopback/tunnel interfaces; it cannot configure addresses. The LAN service stores one profile per node and treats `sites.lan_prefix` as the site's authoritative subnet. The network engine locally authorizes one physical LAN interface. BGP generation/validation assumes one local LAN and one imported/exported prefix per peer. WireGuard AllowedIPs follows that same exact prefix ownership. These assumptions must change together; adding a VLAN form alone is insufficient.

Read existing in-flight changes before implementation. The starting worktree contains extensive unrelated UI, release, network and inventory changes. Reuse the existing LAN validation/transactions, topology locks, draft/deploy workflow, revision publication, telemetry, runtime diagnostics and journaled network recovery. Preserve serialized checksums and old agent compatibility. Current physical BGP and general transit/failover claims remain subject to the evidence limits in [routed LAN operations](../operations/routed-lan.md).

## Operator experience

Keep Underlay focused on physical transport interfaces and optional WAN VLANs. Show interface identity, observed IPv4 addresses, link/admin state, MTU, role, address source, ownership and snapshot age. Show observed gateway/default-route association where available, without treating it as proof of Internet health. Distinguish physical, VLAN, loopback and managed tunnel interfaces; unknown roles stay unclassified until explicitly assigned. Preserve access to the complete inventory.

Open the interface editor directly from the discovered interface row through Configure; open tagged settings through that row's VLANs action. Preselect and lock the reported interface name/parent rather than asking users to re-enter it in a separate form. An interface editor offers role, enabled state, static IPv4/prefix or DHCP client, static gateway and reviewed MTU. Show DNS state; defer DNS editing until resolver ownership is established. Role changes, disabling an active uplink and changing its gateway are disruptive changes and use the same safety transaction as address replacement. A single default uplink is the first release boundary; do not introduce implicit load balancing or automatic WAN failover.

Keep LAN & Routing as the authoritative editor for routed physical LANs and LAN VLANs. An Underlay interface can link to its LAN configuration without duplicating forms or state. VLAN fields: parent Ethernet interface, tag, display name, gateway IPv4/prefix, enabled state and explicit Advertise to fabric setting. Use a routed trunk with tagged subinterfaces. Initial scope excludes bridge/access-port switching, native VLAN/PVID management, QinQ, DHCP server, IPv6, VRFs and overlapping customer networks.

Save draft → review diff/affected devices → Deploy → Received → Applying → Awaiting confirmation → Applied or Rolled back/Failed. These are distinct states; BGP Established, prefix exported/imported and data reachability are separate observations. Show capability/local authorization requirements before deploy, and prevent unsupported edits from being presented as successful. Reuse existing admin/superadmin mutation rules and viewer read-only behavior; local authorization remains mandatory.

## VLAN and routing rules

A VLAN tag identifies a local Ethernet segment. Advertise its IPv4 subnet, never the VLAN number or Ethernet frames. Example: parent `ens34`, tag 100, gateway `10.61.100.1/24` gives approved export `10.61.100.0/24`. A switch trunk must actually carry tag 100; the controller cannot infer cabling or configure an external switch in this scope.

LAN VLAN creation includes an explicit advertisement choice; do not silently advertise every connected route. WAN VLANs carry controller/tunnel transport and cannot export their transport prefixes. Management, default and tunnel prefixes remain excluded. Tag IDs are 1–4094; reject duplicate parent/tag pairs, unsupported parents, recursive VLAN parents, ownership collisions, conflicting addresses and overlapping prefixes. A trunk carrying management is protected as a dependency, including its children; local authorization for one child never grants permission to change the parent or siblings.

Use one authoritative collection of site LAN networks, referenced by device physical/VLAN attachments and distinct host addresses. Replace the single-site-prefix assumption through an additive migration and explicit legacy backfill, preserving existing profiles and shared-site consistency. Do not keep independent writable copies of site prefixes and VLAN advertisements. Define same-site multi-appliance attachment consistency and coordinated renumbering before enabling those mutations. Initially reject ambiguous shared-site changes rather than partially updating appliances.

Compile the approved per-peer prefix sets once for FRR export/import filters, WireGuard AllowedIPs and explicit transit policy. Bound network/peer counts and reject invalid or overlapping ownership. Advertise only successfully installed eligible LANs; remove advertisements on disable/delete or lost local route eligibility, and verify actual FRR withdrawal behavior on link/address loss. Renumber/removal must withdraw old routes and remove old permission/AllowedIPs safely across affected peers. A partial multi-device deployment remains visible and retryable; never claim fleet-wide atomicity.

A BGP route does not authorize traffic. Preserve the existing transit guard until explicit source/destination policy is implemented and lab-verified. Default-deny inter-VLAN and inter-site forwarding; advertisement alone must not enable lateral access. Host-to-host acceptance is a separate policy milestone, with return routes and no implicit NAT.

## Ownership and safe apply

Before choosing a persistence adapter, discover Debian versions and actual owners: bootstrap DHCP helper, FRR static routes, ifupdown, systemd-networkd, NetworkManager and resolver configuration. Support one reviewed appliance ownership arrangement first. Refuse competing ownership; never flush global routes/firewall state or replace FRR's complete configuration. Runtime netlink changes alone do not provide boot persistence.

Extend the existing typed bundle, process lock and durable journal rather than creating another reconciliation daemon. Locally authorize specific physical interfaces and allowed VLAN parent/tag ranges. Keep default installations management-only. Introduce a negotiated schema/capability increment without altering legacy schema bytes; unsupported agents reject safely before any apply. Decide and record the new WAN/DHCP/persistence boundary in an ADR because ADR 0005 explicitly excludes those owners today.

Every disruptive apply validates the complete candidate and dependencies, snapshots only the owned state and previous working persistent configuration, records a pending transaction before mutation, applies in dependency order and uses a bounded confirmation deadline. The appliance must roll back autonomously when controller confirmation is absent, including agent crash/restart and reboot. A controller button or stopping the service is not rollback. Management migration may require a temporary old address/route, but only where the selected network owner supports a proven transition; otherwise require a separate recovery interface and console.

Confirmation binds node identity, revision/checksum and transaction nonce to a fresh authenticated exchange over the intended management path. Prove which interface/source/route was used so a surviving old path cannot falsely confirm the new configuration. Recheck controller DNS/TLS reachability and WireGuard endpoint underlay reachability. DHCP acquisition/renewal, default-route ownership, FRR defaults and resolver changes require explicit coordination. Preserve the prior boot configuration until confirmed, with early-boot recovery for interrupted transactions. Recover locally without controller availability.

## Sequential milestones and acceptance gates

### Fabric agent commit and recovery contract

All appliance configuration is executed by the existing Fabric agent through validated typed operations over its outbound authenticated controller channel. The controller owns desired intent and commit history; the agent owns actual apply, its durable pending transaction and last confirmed working bundle. No SSH execution or arbitrary command editor is introduced.

Deploy offers **Safe commit (60 seconds)**, enabled by default. It is mandatory for changes affecting management, WAN addressing, default routes, VLAN parents carrying transport or other connectivity dependencies. An ordinary commit may be available only for explicitly classified non-disruptive changes under local policy; it still validates, journals and rolls back apply errors. The UI explains the mode and impact before deployment. A confirmed configuration keeps operating during later controller outages; the timer protects a pending commit, not normal disconnected operation.

Safe commit uses these rules:

- Before the first mutation, durably record commit ID, candidate checksum, previous confirmed bundle, affected resources, confirmation policy and a 60-second deadline. Start the budget at the first mutation, including apply time; require successful apply and a fresh confirmation before expiry. A local supervisor/watchdog must enforce the deadline even if the apply worker blocks or exits. Design its interaction with the existing process lock so rollback cannot be blocked indefinitely by a hung apply.
- Show the countdown from agent-reported timing. The controller may confirm only after the agent reports successful apply and completes a fresh authenticated, transaction-bound round trip over the intended path. Offer an optional explicit operator confirmation within the same window. A heartbeat, received acknowledgement, old session or browser click alone cannot confirm applied connectivity. Returning connectivity within the window permits confirmation only after all required checks pass; it does not reset or extend the deadline.
- If the Edge loses controller connectivity during the pending commit and cannot complete confirmation within the 60-second window, restore the previous confirmed runtime and boot configuration locally. Validation/apply failures can trigger earlier rollback. Roll back associated addresses, routes, VLANs, FRR advertisements, AllowedIPs and owned policy as one recovery operation. Keep the rejected candidate from being immediately reapplied by the next desired-revision fetch; require a new explicit deployment/commit ID.
- Persist state transitions before reporting them. Serialize commits per device; reject conflicting deployments while pending/recovering. Make confirmation and rollback idempotent, reject expired or mismatched confirmations, and resolve the confirmation/deadline race under the same transaction ownership. Use monotonic timing within a boot and conservative recovery after restart/reboot or clock changes; never restart a fresh 60-second budget. When deadline validity cannot be established, recover the previous confirmed bundle before accepting new work.
- Distinguish rollback started, rollback succeeded and rollback failed. If restoration fails, retain the journal and bounded failure evidence, expose recovery-required state and provide documented local-console recovery. Do not claim the prior state is restored merely because rollback was attempted.

The 60 seconds are the total pending-commit window, not an extra minute after an earlier timer has elapsed. If a future requirement needs a separate continuous-disconnection grace period, it must be explicitly designed; it must never silently extend this deadline.

### Failure history and correction workflow

Persist a bounded durable agent event outbox before transmission, with commit/event IDs, sequence, timestamps, candidate/previous revision checksums, apply step, result, stable reason code and redacted diagnostic context. Report immediately when connected; after rollback restores connectivity, replay events over the existing channel with bounded retry/backoff and controller deduplication. If rollback does not restore connectivity, retain history locally for later reconnect/console diagnosis; the controller shows outcome unknown/offline until evidence arrives. Define retention, disk bounds and acknowledgement/pruning so pending recovery results cannot be silently lost; refuse new commits when essential journal/history persistence fails.

Add a per-device **Commit history** view using existing history/audit conventions. Show actor, requested and actual times, safe-commit mode, before/after diff, deadline, apply/confirmation/rollback outcome and affected fields. Separate observed facts from suspected causes: `controller_confirmation_timeout` proves confirmation did not arrive, not that a particular gateway was wrong. Other reason codes include validation rejection, local authorization denied, address conflict, DHCP timeout, command failure, interrupted apply and rollback failure. Preserve history immutably and keep access within existing operator roles; sensitive internal diagnostics remain in the restricted diagnostic path.

Provide **Edit and retry** on a failed commit: copy its desired settings into a new draft, highlight the failing field or typed operation, show the failure reason and safe remediation guidance, and compare against the latest confirmed state. Users can fix IP/prefix, gateway, interface, tag or advertisement intent and review a newly generated plan. They cannot edit historical evidence or execute arbitrary shell/FRR commands. Generated operation details may be shown as bounded redacted troubleshooting evidence where authorized; correction happens through validated settings. Revalidate capabilities, local authorization, topology/version and peer impacts before issuing a new commit ID. Retry is explicit, never an automatic loop of the failed candidate.

Build commit metadata, capability/schema support, history API/UI and outbox into milestone 2; prove the local timer, durable recovery and failed-candidate suppression in milestone 3 before any safe apply is enabled. Extend all later routing/WAN gates to cover the full affected bundle. Required focused tests include loss of controller after first mutation, confirmation before/at/after expiry, reconnect without confirmation, duplicate/reordered events, blocked apply, process kill/reboot, clock changes, disk-write failure, failed rollback and edit/retry against changed topology. Real isolated Debian evidence must demonstrate rollback at the 60-second deadline within a documented scheduling tolerance, restored prior state and eventual accurate controller history. Multi-device history must expose individual outcomes and reconciliation needs when some peers confirm and others roll back.

1. **Discovery and ownership design.** Inspect the selected Debian lab and topology using read-only commands; record NIC mappings, switch trunks, management route, current network managers, DHCP/default-route owner and console recovery. Finalize schema limits, local authorization, ADR and acceptance fixtures. Exit: one supported ownership model, explicit management safety design and migration compatibility review. Infrastructure access is required only when this milestone reaches real appliances.
2. **Observed inventory and draft intent.** Extend bounded telemetry with address/type/parent/tag/route and owner/capability observations; introduce additive site-network/interface/VLAN intent and versioned audited APIs. Build editors with existing components and draft review, keeping apply disabled. Exit: authorization, stale-save, overlap, shared-site migration, old-agent compatibility and desktop/mobile/keyboard tests pass; no host mutation.
3. **Dedicated LAN and LAN VLAN safe apply.** Generalize the locally authorized LAN engine to a bounded attachment collection and owned VLAN creation. Validate parent/type/tag/MTU and reject foreign addresses/interfaces. Extend original-state capture, boot persistence and journal recovery under the selected ownership model. Exit: isolated tests prove idempotence, partial failure, interrupted create/delete, drift, rollback, controller loss and reboot; management and unrelated interfaces remain intact.
4. **Multiple-prefix BGP distribution.** Update publication, FRR generation/observations, WireGuard AllowedIPs and all peer validators together. Give BGP router ID a stable explicit ownership rule rather than deriving it from the first editable VLAN. Deploy affected peers with capability checks and visible partial-state recovery. Exit: real FRR isolated tests prove permitted advertisements/imports, forbidden default/management/extra prefixes, withdrawal, deletion, renumbering, unchanged management routes and correct per-peer AllowedIPs. Transit guard remains active.
5. **Explicit forwarding policy.** Integrate approved VLAN prefixes with the existing scoped nftables ownership, anti-spoofing and default denial. Exit: isolated Debian hosts prove allowed/denied inter-VLAN and remote LAN traffic, valid return paths, MTU, restart/reboot and controller-disconnection recovery. BGP success alone cannot pass this gate.
6. **WAN configuration.** First support a dedicated non-management static uplink, then DHCP client and WAN VLAN transport, then active management-interface renumbering as separate gates. Reuse the proven transaction; add locally persisted confirmation timer and chosen network-manager adapter. Exit: isolated Debian tests include invalid gateway, failed DHCP, lost lease/renewal, DNS/controller outage, lost tunnel endpoint route, process kill, reboot during pending apply and autonomous restoration. Active management edits stay disabled until all recovery evidence passes. Multi-WAN failover is separate future scope.

Each milestone requires review of its targeted tests, evidence, change log and rollback before proceeding. Do not publish an agent release or activate physical networking merely because controller forms pass.

Compatibility fixtures cover existing single-LAN records, prior revisions and unsupported agents. Real Debian lab evidence is mandatory for DHCP, persistence, autonomous rollback, reboot and forwarding claims. No production/fleet claim follows from namespace tests.

Rollback controller/UI changes by reverting only milestone deltas while preserving unrelated work. Keep applied migrations immutable and retain existing revisions/audit history. Roll back appliance state through the recorded prior bundle and matching persistent owner; withdraw introduced advertisements and restore exact owned addresses/routes/VLANs/policies in safe order. Preserve identity/private journals. Never remove foreign parent interfaces or flush host networking. Agent downgrade requires explicit schema/LKG compatibility; use a forward fix if older agents cannot read the new journal.

Plan acceptance: editable interface intent and observed state are distinct; VLAN subnet exports are explicit and exact; every applicable peer agrees on allowed prefixes; forwarding remains policy-controlled; loss of controller does not remove confirmed forwarding; disruptive changes self-recover locally. Unimplemented behavior and all appliance results remain UNVERIFIED until their milestone evidence exists.
