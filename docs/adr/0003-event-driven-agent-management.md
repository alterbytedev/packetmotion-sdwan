# ADR 0003 — Event-driven agent management with bounded long-poll

- Status: Accepted and implemented locally in controller and Go agent release 0.1.6; isolated end-to-end NGINX smoke and Debian deployment evidence remain pending.
- Date: 2026-10-15.
- Context: Rama requested a dashboard–Edge communication model similar to NetBird. PacketMotion already has a Next.js Management API, PostgreSQL-backed immutable revisions, outbound Go agents, mTLS, acknowledgements, heartbeat, renewal, and a no-forwarding-through-controller boundary. The current 10–300 second polling interval delays desired-state delivery.
- Decision: Keep Next.js/PostgreSQL as Management and add a bounded agent-initiated HTTPS/mTLS long-poll for desired revisions. Use database notifications only as a wake-up hint; durable reads and reconnects remain the source of truth. Heartbeat, acknowledgement, and certificate renewal remain independent operations. Forwarding stays on Edge/Hub.
- Alternatives: Keep periodic polling (simple but slower); WebSocket/gRPC stream (more persistent and bidirectional but adds runtime, proxy, and connection-lifecycle complexity); separate Management/Signal/Relay services (premature for the current single-controller L3 scope).
- Consequences: Connected devices can receive revisions without waiting for their normal heartbeat interval. The controller must bound waiters, duration, reconnect rate, and database usage; load and wake latency must be measured before fleet claims. PostgreSQL notification loss must not lose state. This does not add peer signaling, relay transport, or network apply.
- Security/recovery: Require the existing mTLS identity and per-node authorization on each wait; no generic RPC or inbound agent port. Controller loss must not alter forwarding. Existing enrollment, revision, acknowledgement, certificate-renewal, and rollback contracts remain in place.
- Verification: Focused controller unit tests, isolated PostgreSQL notification/wait integration, Go tests, typecheck, and signed release checks are recorded in the implementation change log. The Docker/NGINX/Go agent smoke was attempted but the environment's OCI runtime could not execute NGINX (`status 126`). Actual Debian VM, multi-process/fleet load, forwarding, and production evidence remain pending. See [agent control-channel target](../architecture/agent-control-channel.md).
