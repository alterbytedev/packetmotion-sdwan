# Controller–Edge management communication

## Architecture and guarantees

The existing Next.js controller owns server-only domain services and PostgreSQL. The shared Go agent initiates outbound HTTPS by default; dedicated client certificates authenticate Edge/Hub devices through NGINX. The authenticated upstream checks active certificate/node scope on every request, including reused TLS connections. For isolated development labs only, an explicit agent/install flag permits HTTP to private or loopback IPs; the superadmin-configured Settings allowlist controls whether the operator UI emits that flag. HTTP mode exposes enrollment and management traffic. Operator sessions remain separate. No inbound Edge management listener, message broker, streaming service, or generic remote shell is introduced.

Enrollment uses the existing expiring single-use token and locally generated private key. State is private (0700 directory, 0600 files), written using fsync and rename. If a token was consumed but the device never received its identity, an admin can reset enrollment while no heartbeat exists; this revokes the issued certificate and returns the device to pending enrollment. PEM storage is not application-level encrypted; production CA custody and encrypted host storage remain deployment requirements.

## Responsive synchronization target

Agent release 0.1.6 uses an agent-initiated HTTPS/mTLS bounded long-poll on the existing desired-state endpoint. The agent asks the controller to wait up to 25 seconds for a newer revision, independently of its heartbeat cadence. Dashboard publish writes the immutable revision in PostgreSQL and emits a transaction-bound notification as a wake-up hint; each waiter rereads durable state before sleeping and after wake/timeout. A lost notification therefore delays delivery only until timeout. The endpoint remains compatible with older clients that omit `wait`. Pending enrollment keys can be rebound to the supplied controller origin; enrolled identities are not replaceable. This is request/response long-poll, not a persistent bidirectional WebSocket/gRPC stream. See [ADR 0003](../adr/0003-event-driven-agent-management.md) and the [control-channel design and evidence limits](../architecture/agent-control-channel.md).

## Reconciliation and recovery

The source agent keeps renewal, heartbeat, and desired-reconciliation retry deadlines independently while preserving one sequential owner of identity and network state. A failure in one operation does not reset another operation's backoff. Retries grow from one second to a 60-second cap with at most 20% positive jitter; a valid server `Retry-After` may raise the next delay up to the same cap. Heartbeat acceptance releases its pending event independently of configuration success; retry IDs and snapshot remain stable until heartbeat succeeds. The pending heartbeat is memory-only and is replaced after process restart; this is bounded current-state telemetry, not a durable event archive. Because operations remain sequential, an in-flight HTTP request or local reconciliation can delay other due work by its bounded execution time.

A desired revision is validated and staged, then acknowledged received. Pending receipt acknowledgements persist across restart and retry idempotently. Unknown schema/type/fields or invalid LAN prefixes with verified checksums receive rejected acknowledgements; invalid checksums and stale revisions fail locally. Nothing in this channel applies network configuration. Keep the last valid staged state when the controller returns invalid configuration.

## Management path during Hub changes

Signed 0.3.2 fixes keep the enrolled `agentUrl` as the management origin; selecting or removing Hubs does not change it. Startup recovery and normal reconciliation now pass the same local routing authorization, authorized LAN interface, and resolved controller IPs to the network engine. The existing origin-bound `network-management.json` cache supplies safety addresses during DNS failure; it is not an alternate HTTP destination or a way to bypass TLS verification.

Before applying a changed or restored plan, the engine checks every controller IP has an available route outside WireGuard and rejects controller overlap with tunnel addresses, AllowedIPs, the owned LAN, or BGP imports. Route checks also run after replacement before committing the journal. Management confirmation uses a fresh HTTP connection after closing idle connections. Removing the final Hub still checks management safety and cleans up only owned network configuration; reselecting reuses the controller's reserved tunnel addresses and ports.

Keep the enrolled controller origin reachable through the appliance's management/underlay interface independently of Hub tunnels. These checks preserve operator-owned gateways/default routes; they do not create host routes or repair an externally changed route. An unsafe route blocks reconciliation with a bounded error. External routing changes between safety checks can still affect HTTP traffic; this is not continuous enforcement of host routing. DNS cache availability does not guarantee HTTP access during a DNS outage. Do not edit private identity files or disable TLS to work around connectivity failures.

The isolated WireGuard lifecycle test now exercises the real Go HTTP client against a test HTTP listener across removal/reselection and journal recovery, checking the management route and request source address. Its desired/ack/heartbeat handlers are transport fixtures, not the real controller API or full agent scheduler. Actual mTLS controller-to-appliance operation and deployment of this source fix require separate validation. Existing immutable signed bundles are unchanged.

## Device command history

Device details include a superadmin-only Command history view. Its read API rechecks the current database role on every request. History records controller publication, full configuration delivery, agent receipt/rejection, and WireGuard applied/failed/disabled state reports. These are separate events: `received` means staged, and `applied` appears only when the WireGuard agent reports that state. The agent reports current WireGuard state on each reconciliation cycle, so the controller refreshes the latest observation each time but adds a history event only when the state or revision changes. Delivery and receipt retries remain separately numbered events. Each history event has a timestamp, operation ID, revision, operation type, initiating operator when known, and a bounded summary. Superadmins can open or copy the exact serialized configuration snapshot from publication events; the event list loads snapshots separately on demand. Snapshots are bounded to 128 KiB and retained for the same 365-day window. Current controller configs contain no private credentials. Never pass secret material to snapshot storage; future FRR/nftables writers must redact credentials before recording config text. Current WireGuard failure reports do not carry an error reason, so failures use a generic summary.

Events are retained for 365 days and pruned opportunistically when a new history event is recorded; this is not a scheduled cleanup job. Migration 0013 imports existing desired-revision publication timestamps and the latest stored WireGuard observation when they fall within that window; migration 0015 removes consecutive duplicate WireGuard state reports. Older delivery/receipt events or original publisher identity cannot be reconstructed. Pagination and event/operation filters are available on `GET /api/operator/nodes/{id}/command-history`. Future FRR, nftables, or other device operations must use typed operation contracts and report their own outcomes before the history can claim execution. This is not a shell-command log or remote shell.

## Device-reported configuration sources

The superadmin-only **Configuration sources** view separates the controller's published raw snapshot from an on-demand agent report. A request is carried as an optional field in the existing desired-state response, including unchanged responses, and the agent returns it over its authenticated outbound mTLS channel. Creating the durable request also emits the existing PostgreSQL notification hint, so a bounded desired wait can return promptly; the request row remains authoritative if the hint is lost. The agent submits a delivered report before validating, staging, acknowledging, or applying the accompanying desired revision, so those failures do not starve collection. Older agents ignore the optional field; the request then expires as unavailable after two minutes. The latest request/report per device is retained for 24 hours and replaced by a later request. No new inbound connection or arbitrary file/command API is introduced.

The source agent reports only the known state directory paths, file presence, its persisted WireGuard applied plan, PacketMotion-owned WireGuard interface presence/address/up state and peer handshake timestamps. When local WireGuard collection is disabled, it returns the basic revision and known file-presence report without querying kernel interfaces. It checks paths with `lstat`, reads only `network-applied.json`, and does not open the private key file. The report does not contain private or preshared keys; its complete serialized request, including the JSON envelope, is limited to the controller's 32 KiB ingress bound. Empty `allowedPrefixes` may be omitted by older Go struct serialization and is normalized to an empty array; malformed values remain rejected. `/var/lib/packetmotion` is the default `--state-dir`; the agent reports the actual directory when overridden. WireGuard is applied through kernel interfaces, not `/etc/wireguard/*.conf`. FRR `/etc/frr/frr.conf` is a host reference only; general FRR configuration is not collected or managed. The owned WireGuard nftables guard is a runtime `inet pmwg…` table; general nftables state is not collected. The report is not a full host configuration audit. Migration 0016 adds the latest-report table and 0019 adds nullable `unavailable_reason` values `timeout` and `collection_failed`. The controller owns timeout marking; agent reports may only identify collection failure. Older rows display an unknown reason. Expired rows are pruned opportunistically on state requests and reads. The diagnostic and retry fixes are packaged in signed agent 0.3.1 Linux amd64/arm64 bundles under the controller public assets; immutable 0.3.0 bundles predate these fixes. Deploy the matching controller source and migrations through 0019 before upgrading devices. Local packaging is not evidence of live deployment or a completed appliance report. Existing devices must run a diagnostic-enabled agent to return reports; the controller has no remote shell or agent-initiated software-install operation, so installation must be initiated on the device host.

The read-only `/api/ready` check verifies the core tables and columns used for device authentication, desired retrieval, acknowledgements, heartbeat, and certificate renewal. It does not apply migrations or require optional diagnostic, command-history, or dashboard schema. Apply migrations through 0019 before deploying this source. A missing required schema returns a generic not-ready response with a request reference; database errors remain generic and are correlated through the same reference.

For unchanged revisions the agent checks its cached file and supplies revision/checksum. The controller returns a small unchanged marker only if both match the device's latest revision. Missing/corrupt cache causes full retrieval and repair. Successful unchanged receipts do not write state or repeat acknowledgements. Fetch and acknowledgement races with a new publish produce a conflict; the next cycle fetches the newer revision.

Renewal persists the replacement before switching clients, preserving the old identity on errors. Existing overlapping-certificate issuance tolerates response loss. If a certificate expires while disconnected, ordinary mTLS renewal cannot recover; use an authorized operator and the existing enrollment/revocation recovery workflow. Never disable TLS verification or erase identity as an automatic retry.

## Timing and capacity

Telemetry is sampled on the configured healthy interval of 10–300 seconds. Desired-state waits are capped at 25 seconds and shortened when heartbeat or renewal is due; a publish can wake them immediately without causing an extra heartbeat. Normal startup adds up to five seconds of jitter; `run --once` skips startup delay and does not wait. Each operation uses its own exponential retry from one second through 60 seconds with at most 20% positive jitter. Valid server retry hints are bounded by 60 seconds. Sequential HTTP and reconciliation work can delay other operations by the bounded call duration. No latency SLA is established.

HTTP connections are bounded to two per origin with handshake/header/overall deadlines and idle connection cleanup. Heartbeats follow the configured interval; desired-state waits reconnect at most every 25 seconds, and a new revision adds an acknowledgement. Each active wait holds one HTTP connection and one PostgreSQL LISTEN connection per controller process, plus short database reads; only one wait per node per process is accepted and total waiters are capped at 2,000. Approximate steady request rate is heartbeat count / configured interval plus up to device count / 25 seconds for waits, excluding acknowledgements, renewals, retries, and reconnects. Fleet sizing and multi-process waiter coordination have not been measured. PostgreSQL heartbeat processing remains transactional with bounded retention of 100 samples per device; deduplication is limited to retained event IDs. Configuration history remains immutable and has no new retention policy.

The isolated `npm run test:agent` smoke includes real Go agent long-poll wake-up after dashboard publish and also measures 40 authenticated unchanged reads over eight concurrent connections. The previous 2026-10-14 sample (before long-poll) completed in 141.3 ms with 68.7 ms p95 and zero failed reads; it is not a long-poll performance result. The updated end-to-end smoke is UNVERIFIED because Docker could not execute its NGINX container in this environment. PostgreSQL long-poll wake/timeout behavior and Go unit tests pass. This does not simulate a fleet, heartbeat write load, retry storms, WAN latency, or production deployment. Production fleet capacity, Debian service/reboot behavior and data-plane forwarding remain UNVERIFIED. Before a pilot, run sustained mixed heartbeat/config/renewal traffic at the intended device count and intervals; record p95/p99 latency, errors, PostgreSQL pool/lock pressure, CPU/memory, outages/reconnects and resource limits before setting capacity or latency commitments.

## Deploy and rollback

Deploy the controller first, then agent binaries. No migration is introduced by this hardening. Existing clients continue to receive full desired responses; new agents accept full responses from old controllers. See the [ingress guide](../../deploy/proxy/README.md) and [agent guide](../../sdwan-edge/README.md). Never expose the private controller upstream or proxy secret.

Before a canary upgrade, separately authorize an isolated Debian device and proxy with console rollback; apply controller migrations through 0019 in a test database and verify readiness. Record exact controller source/API and agent binary versions, confirm the signed release distinction, and capture baseline heartbeat, desired revision receipt, and certificate expiry/renewal state. Exercise: (1) a basic diagnostic with local WireGuard collection disabled and confirm no network observations are claimed; (2) invalid desired configuration alongside a diagnostic and confirm both outcomes are visible; (3) report retry, duplicate delivery, timeout/expiry, and request replacement; (4) controller outage and recovery; (5) renewal, agent restart, and heartbeat retry identity. Capture redacted request IDs and outcomes as PASS/FAIL/UNVERIFIED for every scenario. Stop on management-path degradation and restore the prior source/binary using the existing recovery procedure. Do not use production networking for fault injection or expand to a fleet based on this checklist. All these post-change canary scenarios remain **UNVERIFIED** until executed in the separately authorized isolated environment.

Rollback by deploying the controller handler with immediate desired responses and agent 0.1.2 periodic-polling binaries, preserving identities, revision records, audit data, schema and append-only change logs. No database migration is introduced. Dashboard appearance/auth and privileged network state are unchanged.

## Connection diagnostics and agent operation logs

The authenticated operator endpoint `GET /api/operator/nodes/{id}/connection-status` exposes only current lifecycle facts for non-archived devices, not diagnostic runtime logs. Overview → Connection check reads it on mount and on manual refresh, shows the check timestamp and at most ten allowlisted audit-event summaries, and explains pending enrollment, expired tokens, accepted enrollment without heartbeat, stale heartbeat, rejected/missing receipt, and revoked access. Admins and viewers can read these operational summaries; raw runtime-error browsing remains superadmin-only. Failures use the existing generic error/reference correlation path and no-store response policy. There is no unauthenticated diagnostic endpoint or new persistence owner.

Signed 0.3.2 agents emit JSON journal lines for enrollment/startup/network recovery and separate renewal, heartbeat and desired-operation outcomes. Fields include UTC time, operation, outcome, safe code, validated HTTP status/reference, node/revision and the scheduled retry time. The first outcome, changes/recovery, and unchanged results at most once per minute are logged per operation. Error messages, raw causes, URLs, bodies, credentials and TLS material are excluded. Operation errors remain independently retried by the existing sequential scheduler. Per-operation log suppression resets on process restart, and journal retention follows the host systemd-journald policy. These logs are local to Debian; no log-upload channel or diagnostic-log role expansion is introduced. A process that cannot start or authenticate cannot send its local reason to a new pending dashboard identity; the UI explicitly marks that observation limit. Existing snapshot/audit retention and private-state permissions remain unchanged.
